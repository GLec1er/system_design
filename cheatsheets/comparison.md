# Сравнение глав: что выбрано и почему

Все главы в одной таблице: где лежат данные, через что идут события и какое свойство задачи к этому привело. Цель страницы: видеть не «в главе N стоит Cassandra», а «при таком профиле нагрузки берут такое хранилище».

## Какое хранилище при каком профиле

| Профиль задачи | Что берут | Главы |
|---|---|---|
| Нужны транзакции и ограничения, нагрузка умеренная | Реляционная БД | 7, 11, метаданные в 9 |
| Чтений много, данных мало | Реляционная БД с репликами и кэш | 1 |
| Поток записи, чтение по одному ключу, без JOIN | Wide-column NoSQL (Cassandra, Bigtable) | 2, 3, 6, 8, 17, 21, 22 |
| Данные живут минуты, нужна скорость памяти | Redis с TTL | 2, 17 (лимиты) |
| Нужен ранг или сортировка на лету | Redis sorted set | 10 |
| Большие неизменяемые файлы | Объектное хранилище | 3, 8, 9, 17 (веса) |
| Ряды чисел по времени | TSDB | 5 |
| Агрегаты по миллиардам строк | Колоночная OLAP | 15 |
| Всё и навсегда, читают пакетом | Озеро: HDFS или S3, Parquet | 14, 15, 16, 18 |
| Поиск по тексту | Обратный индекс | 8 |
| Поиск похожего | Векторный индекс | 18, 19 |
| Позиции движущихся объектов | Ячейки в памяти (H3, geohash) | 23 |
| Микросекунды | Память одного процесса | 13 |
| История и воспроизводимость важнее состояния | Журнал событий | 12, 13 |

## Когда нужна шина, а когда нет

| Ситуация | Что берут | Главы |
|---|---|---|
| Событие читают несколько независимых потребителей | Kafka | 3, 10, 15, 16, 18 |
| Приёмник медленнее источника или может упасть | Kafka как буфер | 5, 8, 15 |
| Нужно перечитать после сбоя | Kafka с хранением | 6, 15, 16 |
| Задачи с повторами, паузами и DLQ | Очередь задач | 11 |
| Рассылка без хранения, потеря не страшна | Redis Pub/Sub | 2 |
| Пользователь ждёт результат | Без очереди, синхронно | 7, 9 |
| Сеть слишком медленна | Свой журнал в памяти или на локальном диске | 12, 13 |

## Одно и то же решение в разных главах

| Решение | Где | Что его вызвало |
|---|---|---|
| Идемпотентный ключ | 7, 11, 12, 15, 17, 21, 22, 23 | Повтор запроса не должен выполниться дважды |
| Ключ раздела по пользователю | 2, 8, 15, 17, 18 | Все данные человека читаются вместе |
| Данные отдельно от метаданных | 8, 9 | Они растут с разной скоростью и по-разному читаются |
| Денормализация под запрос | 8, 9 | В шардированном хранилище нет JOIN |
| Event time и watermark | 6, 15 | События опаздывают |
| Exactly-once по эффекту | 6, 11, 15, 16 | Сбой посреди пачки |
| Сверка | 11, 12, 16 | Нужно доказать, что данные сошлись |
| Мощность не в запросах | 9 (байты), 17 (токены), 18 (оценки модели) | Запрос плохо описывает нагрузку |
| Воронка от дешёвого к дорогому | 1 (ячейка, потом точное расстояние), 18 | Точная проверка слишком дорогая для всех |

## Как пользоваться на интервью
1. Назвать профиль: что чаще, чтение или запись; сколько данных; нужны ли транзакции; сколько можно ждать.
2. По профилю назвать хранилище и сказать, чем платим.
3. Спросить себя, ждёт ли пользователь результат. Если нет и потребителей несколько, ставить шину.
4. Сказать, какое требование заставило бы выбрать иначе.
