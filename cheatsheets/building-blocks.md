## Rate limiter
**Проблема:** один клиент или бот забирает всю мощность; нужна защита от перебора и DDoS.

| Алгоритм | Как работает | Плюс | Минус |
|---|---|---|---|
| **Token bucket** | Ведро на N токенов пополняется с постоянной скоростью; запрос забирает токен | Пропускает короткие всплески, два понятных параметра | Параметры надо подбирать |
| **Leaking bucket** | Запросы встают в очередь и уходят с постоянной скоростью | Ровный поток на выходе | Всплеск ждёт в очереди, свежие запросы отбрасываются |
| **Fixed window** | Счётчик на окно (минуту), в начале окна сброс | Просто и дёшево | На стыке окон пройдёт вдвое больше лимита |
| **Sliding window log** | Храним время каждого запроса, считаем за последние N секунд | Точно | Много памяти |
| **Sliding window counter** | Счётчик текущего окна плюс доля предыдущего | Почти точно и дёшево | Приближение |

- **Где ставить:** на входе (API Gateway), до дорогой логики. Ключ лимита: пользователь, IP, токен API.
- **Где хранить счётчики:** Redis. Проверка и увеличение должны быть атомарны (Lua-скрипт или `INCR` с `EXPIRE`), иначе два сервера пропустят лишнее.
- **Что отвечать:** `429 Too Many Requests` с заголовком `Retry-After`. Клиент обязан его уважать.
- **Жёсткий или мягкий:** отбросить, поставить в очередь или пропустить с пониженным приоритетом.
- **В главах:** глава 7 (боты в распродажу), глава 11 (защита API), глава 13 (DDoS на шлюз). Родственные приёмы: [load shedding и backpressure](resilience.md).

**Фраза:** «Token bucket на шлюзе, счётчики в Redis с атомарной проверкой, клиенту 429 и Retry-After».

## Consistent hashing
**Проблема:** `hash(key) % N` при добавлении или потере сервера переносит почти все ключи: кэш сбрасывается разом.

- **Как:** серверы и ключи ложатся на одно кольцо по хэшу. Ключ принадлежит первому серверу по часовой стрелке. При добавлении сервера переезжает только соседний участок: в среднем `k / n` ключей.
- **Виртуальные узлы:** каждый сервер занимает на кольце сотни точек. Нагрузка выравнивается, а мощный сервер получает больше точек.
- **Цена:** кольцо надо хранить и раздавать всем клиентам (service discovery); при смене состава часть ключей всё равно переезжает.
- **Варианты:** фиксированные слоты (Redis Cluster делит 16 384 слота между узлами), rendezvous hashing (для каждого ключа выбирается сервер с наибольшим хэшем пары ключ-сервер).
- **В главах:** глава 2 (каналы по серверам Pub/Sub), глава 5 (цели между сборщиками метрик), глава 10 (слоты Redis Cluster), глава 12 (счета по шардам).

**Фраза:** «Кольцо с виртуальными узлами: при смене состава переезжает только доля ключей, а не всё».

## Фильтр Блума и вероятностные структуры
**Проблема:** надо дёшево ответить «этого элемента точно нет», не храня сами элементы.

- **Как:** массив из m бит и k хэш-функций. Добавление ставит k бит. Проверка: если хоть один бит нулевой, элемента точно нет; если все единицы, возможно, есть.
- **Свойства:** ложноотрицательных ответов нет, ложноположительные есть. Около 10 бит на элемент дают примерно 1% ошибок. Удалять нельзя (для этого счётный вариант).
- **Где применяют:** LSM-хранилища (не читать с диска файл, в котором ключа точно нет), защита кэша от запросов по несуществующим ключам, дедупликация.

| Структура | Вопрос | Память |
|---|---|---|
| **Bloom filter** | Есть ли элемент? | ~10 бит на элемент |
| **HyperLogLog** | Сколько уникальных? | килобайты на миллиарды, ошибка около 1% |
| **Count-Min Sketch** | Сколько раз встретился элемент? | фиксированная таблица, завышает |

- **В главах:** глава 8 и 12 (LSM под капотом), глава 6 (топ-100 объявлений: при очень большом числе ключей частоты считают приближённо).

## Генерация уникальных ID
**Проблема:** идентификатор нужен до записи в БД, на многих узлах сразу, без общей точки отказа.

| Способ | Плюс | Минус |
|---|---|---|
| **Автоинкремент** | Короткий, упорядочен | Одна БД; при шардах нужен шаг и смещение; выдаёт число записей |
| **UUID v4** | Генерируется где угодно без координации | 128 бит, не упорядочен: вставки разбросаны по индексу |
| **UUID v7, ULID** | Упорядочен по времени, без координации | 128 бит |
| **Snowflake** | 64 бита, упорядочен по времени | Зависит от часов; нужен номер машины |
| **Сервис выдачи** (ticket server) | Простые числа | Единая точка отказа, надо резервировать |

- **Snowflake:** 1 бит знака, 41 бит времени в миллисекундах (хватает примерно на 69 лет), 10 бит на дата-центр и машину, 12 бит счётчика (4096 ID в миллисекунду на машину).
- **Что спросить у себя:** нужна ли сортировка по времени, сколько бит, можно ли раскрывать объём, где рождается ID (у клиента, чтобы служить ключом идемпотентности).
- **В главах:** глава 7 (`reservation_id` рождается до запроса), глава 11 (`payment_order_id`), глава 9 (`object_id` и TIMEUUID для версий), глава 13 (sequencer выдаёт номера по порядку).

## Key-value хранилище в стиле Dynamo
Сборка из предыдущих кирпичей; на ней стоят Cassandra и DynamoDB (главы 2, 6, 8).

| Задача | Приём |
|---|---|
| Разложить данные | Consistent hashing с виртуальными узлами |
| Не потерять | Репликация на N узлов по кольцу |
| Согласованность по выбору | [Кворум](theory.md#5-кворумы) W и R |
| Конфликты | Векторы версий или «последний победил» |
| Узел временно недоступен | Hinted handoff |
| Узел надолго отстал | Anti-entropy на деревьях Меркла |
| Кто жив | Gossip: узлы обмениваются heartbeat-таблицами |
| Быстрая запись | Журнал → таблица в памяти → файлы на диске (LSM) |
| Быстрое чтение | Память → фильтр Блума → нужный файл |

## Балансировщик и API Gateway
- **L4** смотрит IP и порт: очень быстрый, не видит URL. **L7** разбирает HTTP: маршрутизация по пути, снятие TLS, повторы; дороже по CPU.
- **Алгоритмы:** round robin, least connections, хэш по клиенту (sticky).
- **Проверки здоровья:** активные (опрос) и пассивные (по ошибкам ответов). Упавшая копия выпадает из пула.
- **API Gateway** это L7-балансировщик плюс общие обязанности: аутентификация, лимиты, маршрутизация по сервисам, логирование.
- **В главах:** 1, 2, 3, 7, 8, 9. Балансировщик сам должен быть резервирован.

## CDN
- **Pull:** CDN забирает файл с origin при первом запросе и хранит по TTL. **Push:** мы сами выкладываем файлы.
- **Инвалидация:** дорогая и медленная. Проще версия в имени файла: новый файл это новый URL.
- **Что класть:** неизменяемое и общее для всех: тайлы, картинки, вложения, статические страницы.
- **Цена:** платим за трафик; персональные данные через CDN идут только по подписанным URL.
- **В главах:** глава 3 (тайлы), глава 7 (страницы отелей), глава 8 (вложения), глава 9.

## Стратегии кэша
| Стратегия | Как | Когда |
|---|---|---|
| **Cache-aside** | Приложение читает кэш, при промахе идёт в БД и кладёт в кэш | По умолчанию |
| **Read-through** | То же, но в БД ходит сам кэш | Когда кэш это библиотека или сервис с загрузчиком |
| **Write-through** | Запись идёт в кэш и синхронно в БД | Нужны свежие чтения |
| **Write-behind** | Запись в кэш, в БД пачками позже | Очень много записи, потеря допустима |

**Вытеснение:** LRU (давно не читали), LFU (редко читали), TTL.

**Три беды кэша:**
- **Penetration:** запросы по ключам, которых нет в БД, каждый раз идут в БД. Лечится кэшированием «пусто» и фильтром Блума.
- **Stampede:** горячий ключ истёк, тысячи запросов разом идут в БД. Лечится блокировкой на пересчёт или обновлением до истечения.
- **Avalanche:** много ключей истекли в одну секунду или кэш упал. Лечится случайным сдвигом TTL и репликами.

В главах: 1, 2, 5, 7, 8, 9. Общая схема в [паттернах](README.md#кэширование-и-инвалидация).

## Доставка событий клиенту
| Способ | Как | Когда |
|---|---|---|
| **Short polling** | Клиент спрашивает по таймеру | Редкие обновления, простота |
| **Long polling** | Сервер держит запрос до события или таймаута | Нет WebSocket, события нечастые |
| **SSE** | Один долгий HTTP-ответ, сервер пишет события | Поток только от сервера к клиенту |
| **WebSocket** | Двустороннее постоянное соединение | Чат, локации, торги |

Цена постоянных соединений: серверы с состоянием, сложнее балансировка и выкатка (глава 2: graceful drain).

## Рассылка: при записи или при чтении
- **Fan-out on write:** при событии сразу кладём его всем подписчикам. Чтение мгновенное, запись дорогая; у автора с миллионом подписчиков запись превращается в лавину.
- **Fan-out on read:** собираем ленту в момент чтения. Запись дешёвая, чтение дорогое.
- **Гибрид:** обычным пользователям при записи, знаменитостям при чтении.
- **В главах:** глава 2 это fan-out on write через Pub/Sub; оценка в 14 млн доставок в секунду ровно про это.

## Поиск
- **Обратный индекс:** слово → список документов. Запрос пересекает списки. Elasticsearch и Lucene устроены так.
- **Маршрутизация:** если все запросы внутри одного пользователя, документы пользователя кладут в один шард (глава 8).
- **Индекс отстаёт** от основной БД: наполняется через очередь или CDC.
- **Автодополнение:** префиксное дерево (trie) с заранее посчитанным топом в каждом узле.

## Вопросы для повторения
<details><summary>Чем token bucket отличается от leaking bucket?</summary>

Token bucket пропускает всплеск, пока есть токены. Leaking bucket выдаёт ровный поток, всплеск ждёт в очереди.
</details>
<details><summary>В чём беда fixed window?</summary>

На стыке двух окон за короткое время проходит вдвое больше лимита.
</details>
<details><summary>Зачем виртуальные узлы?</summary>

Без них участки кольца неравны и нагрузка перекошена. Сотни точек на сервер выравнивают её и позволяют учесть разную мощность.
</details>
<details><summary>Что гарантирует фильтр Блума?</summary>

«Нет» всегда верно. «Есть» может быть ошибкой.
</details>
<details><summary>Из чего состоит Snowflake ID?</summary>

Время в миллисекундах (41 бит), номер дата-центра и машины (10 бит), счётчик внутри миллисекунды (12 бит).
</details>
<details><summary>Чем плох UUID v4 как первичный ключ?</summary>

Он случаен: вставки попадают в случайные страницы индекса, кэш страниц работает плохо. UUID v7 упорядочен по времени.
</details>
<details><summary>Какие три беды у кэша?</summary>

Penetration (ключей нет в БД), stampede (горячий ключ истёк), avalanche (много ключей истекли разом).
</details>
